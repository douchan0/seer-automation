### 关键结论（都有实测支撑）

1. **旧日志里的"截图 138ms / OCR 240ms"：截图部分基本准确，OCR 部分偏乐观**（实测 146ms @ load 5.7，但 load 37 时 483ms、load 85 时 685ms）。
2. **单次截图 API 对尺寸不敏感**（全图 2298×1428 vs 300×200 ROI 几乎同价）——
   "ROI 截图更快"这个直觉是**错的**，ROI 收益只能来自下游像素量减少。
3. **常驻 SCStream 才是正确的截图架构**：读最新帧 0.04 ms，帧龄 ≤ 17 ms。
4. **SCK 是变化驱动的**：静止画面 5 秒只给 4–14 帧。执行器必须"自己按节拍轮询读最新帧"，
   **绝不能阻塞等下一帧**，否则在菜单/弹窗界面会永久挂起。
5. **OCR 仍是新方案里最大的一块（76.9%）**：所以状态识别必须走亚毫秒指纹/ROI 模板，
   OCR 只作为 `UNKNOWN` 超时后的升级手段。
6. **输入 API 本身不是瓶颈**（提交 0.015 ms），但旧代码每次点击硬编码了 **67 ms** 的 `usleep`，
   这是自加的、可以去掉的成本。
7. **⚠️ 更正我在 Round 1 早期的说法**：我曾说"OCR 占 84%，截图只占 16%"。
   那是**通用窗口（WPS 文档，45–95 个文本框）**测出来的，**不是游戏内容**。
   在真实游戏内容上，实测是**截图+解码 53.9% / OCR 46.1%**。
   两个数字都保留在 `docs/PERFORMANCE_BASELINE.md` §9，用来证明"这个比例取决于画面上的文字量"。

### 测量方法学问题（重要，且已实际纠正）

**本轮所有测量都在多个 Agent 并行占用机器的条件下完成**，`vm.loadavg` 一度高达 **85**（8 核）。
这不是小事，它实际造成过三次误判，全部已修正并记录：

| # | 误判 | 真相 |
|---|---|---|
| 1 | "OCR 是 469 ms" vs "OCR 是 159 ms"，两个 Agent 对不上 | **OCR 延迟随负载放大约 4 倍**：load 5.7→146 ms、10.5→159 ms、37→483 ms、85→685 ms。两个数都对，是负载不同 |
| 2 | "PNG 解码只要 0.06 ms，可忽略" | `CGImageSourceCreateImageAtIndex` **是惰性的**，只返回句柄不解码。**强制解码 36.9 ms @ load 7.5（负载 37 时 144 ms）**——差 300 倍 |
| 3 | "OCR 占 84%，截图只占 16%" | 那是**通用窗口**（WPS 文档 45–95 个文本框）的比例。**真实游戏内容上是截图+解码 53.9% / OCR 46.1%** |

因此本轮确立的**测量纪律**（写进 `AGENTS.md`）：
- **任何延迟数字必须附带当时的 loadavg 与核数**，否则不可复现。
- **同一次运行内的比值可信**，跨运行的绝对值不可直接比较。
- 收尾已执行一次 `QUIESCED-FINAL` 重跑（load 5.74–7.48，0.72–0.93/核），
  `PERFORMANCE_BASELINE.md` 引用的就是这一次；`LOADED` 系列全部保留并标注。
- 只有在**同一次迭代内**打的阶段时间戳才允许用来做占比分解；
  跨后端相减得到的"派生占比"已从文档中**撤下**（曾出现 305.71 ms 与 133.4 ms 自相矛盾）。

## Round 3.5 — 原生 SCK 守护进程（补上 Round 4 的第一号缺口）✅ 完成

**时间**：2026-11-01 23:21 – 23:40

### 为什么做这一轮

Round 4 的三个前置缺口里，排第一的是「**原生 ScreenCaptureKit 守护进程未实现**」：
`DaemonCapture` 只对假守护进程测过协议，实际可用路径仍是 **164 ms/次** 的子进程，
真实战斗循环根本跑不起来。这一项**不需要游戏也能做**，所以先做。

### 完成了什么

1. 写出 `native/seerdx.swift`（≈600 行）→ `native/bin/seerdx`，完整实现 `seerauto/PROTOCOL.md`：
   常驻 SCStream 预热会话、非阻塞 `capture.latest`、`capture.roi` 原生裁剪、
   一次性 `shot`、`ocr`、`click/move/key/type`、`win/pin/activate`、`caps` 能力发现。
2. 规避了本轮总结出的三个坑：
   - **绝不在主线程阻塞等 SCK 异步结果**（会死锁，实测 13 分钟挂死）→ 改成
     主线程 pump run loop + 命令队列，stdin 读线程独立。
   - **帧不走 PNG**（编解码约 75 ms，会把收益全吃掉）→ 改用**原始 BGRA + 双缓冲文件**，
     协议新增 `fmt: "bgra"`，Python 按 `(seq, w, h, stride, rect)` 缓存解码结果。
   - 缓冲区**只分配一次**，逐帧 memcpy。
3. `seerauto/capture.py` 增加 `read_raw_bgra()` 与解码缓存（同 seq 不重复解码）。
4. `--target <name>` 参数：让守护进程可以对普通窗口运行，**没有游戏也能测**。
5. 新增 `tools/build_seerdx.sh`、`bench/bench_daemon.py`。

### 本轮后续修复：把"乱点"改成"每回合一次"

首版连战虽然全胜，但**每回合点了约 2 次**（172 次点击 / 3 场）。原因是等待循环 0.35 s 后重判，
此时游戏仍在播动画、战斗态没有退出，于是又点了一次 —— 而这些点击会被游戏排队，属于**噪声**。

修法（`tools/battle_run.py`）：
1. 用**战斗日志区域的像素指纹变化**当作"回合已开始"的信号（亚毫秒，不用 OCR）；
2. 变化之后**再等画面稳定**（日志指纹在 `--stable-ms` 内不再变化）才做下一次决策；
3. 点怪后**等战斗 UI 真正出现**（最多 6 s），不再每 1.4 s 重复点同一只怪。

修复前后对比（同样打 2–3 场，全胜）：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 每场点击次数 | ~57 | **~17** |
| 等待均时长 | 362 ms（乱点，回合没真推进） | **2961 ms（真实回合节奏）** |
| 每场战斗时长 | ~46 s | ~45 s |

**关键结论：回合实际耗时约 3 s、每场约 13 回合，这是游戏自身的动画速度，不是我们的开销。**
"等待变长"恰恰说明循环现在**遵守游戏节奏**而不是抢跑。

真正的引擎开销是每轮 **capture 27 ms + detect 8 ms = 35 ms**，
占回合总时间的 **约 1.2%** —— 也就是说，**视觉循环已经完全不是瓶颈了**。
